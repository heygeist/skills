# Intake

Inspect first, then ask only for missing decisions.

## Identity and audience

- Product, project, or organization name and plain-language description
- Audience, familiarity level, positioning, and desired reaction
- Official terminology, claims, limitations, and prohibited framing
- Common post subjects and concepts that require explanation

## Channels and copy

- Target platforms and default platform
- Default language and platform-specific language variants
- Voice, paragraph rhythm, CTA, links, mentions, hashtags, and avoidances
- Short approved examples; never promote a post-specific caption into a permanent rule without confirmation

## Visual system

- Canonical design guide or design-token source
- Color roles, typography, spacing, shape, elevation, and component treatments
- Composition, hierarchy, whitespace, imagery, screenshot, logo, mascot, and illustration behavior
- Platform-specific visual variants and visual do/don't rules

## Assets and references

Accept pasted material, local files, URLs, screenshots, brand guides, and design files. For each reusable file, resolve:

- Category: `logos`, `mascots`, `icons`, `illustrations`, `photos`, `fonts`, `templates`, `references`, or `other`
- Semantic role and `canonical` or `reference-only` status
- Original location or URL
- Ownership, license, and restrictions

Copy remote material only after the user confirms usage rights and it exists as a readable local file. Preserve canonical assets unchanged. Put examples used only for analysis in `references`.

## Inference

An inference is a proposed rule observed across examples but not explicitly declared. Present it as a question, such as: “These examples consistently reserve orange for calls to action. Should that become a design rule?”

Only confirmed inference may enter `DESIGN.md`, `context.md`, or `caption.md`. When sources disagree, report the conflict and ask which source is canonical.
